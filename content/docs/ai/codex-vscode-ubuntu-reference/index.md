## [在 Ubuntu/Linux 上通过 VS Code 使用 Codex ](https://www.cnblogs.com/sove-reign/p/19718670)

Codex 提供了 VS Code IDE 扩展，支持直接在编辑器中调用代码能力。对于 Ubuntu/Linux 用户来说，整体使用流程并不复杂：安装插件、完成登录、开始使用即可。
不过，在实际配置过程中，很多人会卡在登录环节，尤其是在代理网络环境下，常见报错如下：

```text
Token exchange failed: token endpoint returned status 403 Forbidden
```

这类问题通常并不是插件本身安装失败，而往往与 **VS Code 没有正确使用代理配置** 有关。本文将围绕插件安装、登录报错原因以及解决方法，给出一套适合 Ubuntu/Linux 用户的清晰操作方案。

---

### 一、安装 Codex 插件

首先，在 VS Code 中安装 Codex 插件。

#### 安装步骤

1. 打开 VS Code
2. 进入左侧 **Extensions（扩展）**
3. 搜索 **Codex**
4. 安装对应插件
5. 安装完成后重启 VS Code
6. 在侧边栏或命令面板中打开 Codex，开始登录

安装完成后，通常会弹出登录提示。此时可以按照插件指引继续进行认证。

---

### 二、登录时报错：`Token exchange failed 403`

在 Linux 环境下，Codex 的登录流程通常需要经过浏览器授权，再将认证结果返回给 VS Code 插件。如果这个过程中网络请求没有正常发送，就可能在 token 交换阶段失败，并报出如下错误：

```text
Token exchange failed: token endpoint returned status 403 Forbidden
```

很多用户看到 403 会误以为是账号问题，实际上更常见的原因是：

- 浏览器可以正常打开登录页面；
- 但 VS Code 插件本身没有正确继承代理设置；
- 导致插件向认证服务发起请求时失败；
- 最终在 token exchange 阶段报 403。

因此，这类问题的重点不在“重新安装插件”，而在于**显式配置 VS Code 的代理设置**。

---

### 三、解决方法：修改 `settings.json` 显式覆盖代理配置

如果你在 Ubuntu/Linux 上使用本地代理，例如常见的 `127.0.0.1:7890`，可以通过修改 VS Code 的用户配置文件，让插件网络请求明确走代理。

#### 配置文件路径

在 Linux 下，VS Code 用户配置文件通常位于：

```text
~/.config/Code/User/settings.json
```

如果文件不存在，可以手动创建。

---

### 四、添加代理配置

打开 `settings.json`，**直接在{ }里面加入以下内容，注意原本内容的最后一行，应补上逗号**：

```json
  "http.proxy": "http://127.0.0.1:7890",
  "http.noProxy": [
    "127.0.0.1",
    "localhost",
    "::1"
  ],
  "http.proxySupport": "override"
```

---

### 五、保存并重启 VS Code

完成修改后，按以下步骤操作：

1. 保存 `settings.json`
2. 完全退出 VS Code
3. 重新打开 VS Code
4. 再次进入 Codex 插件
5. 重新执行登录流程

这一步非常重要。
如果只保存配置但不重启，旧的网络配置可能仍然被缓存，导致修改没有真正生效。

---

### 六、配置项说明

为了避免只是“照抄配置”，这里对每个字段做一个简要说明。

#### 1. `http.proxy`

```json
"http.proxy": "http://127.0.0.1:7890"
```

这个字段用于指定 VS Code 所使用的代理地址。
其中 `127.0.0.1:7890` 只是一个常见示例，你需要根据自己本机代理工具的实际端口进行修改。

---

#### 2. `http.noProxy`

```json
"http.noProxy": [
  "127.0.0.1",
  "localhost",
  "::1"
]
```

这个字段表示哪些地址不走代理。
将本地回环地址加入白名单后，可以避免 VS Code 在访问本地服务时错误地通过代理转发。

---

#### 3. `http.proxySupport`

```json
"http.proxySupport": "override"
```

这是最关键的一项配置。
它的作用是让 VS Code 在处理扩展相关网络请求时，**优先使用你显式指定的代理设置**，而不是模糊依赖系统环境变量或自动继承机制。

很多情况下，正是因为 VS Code 或插件没有正确继承系统代理，才会导致浏览器能登录、但插件无法完成 token 交换。设置为 `override` 后，通常能显著提高成功率。

---

### 七、为什么这个方法有效

很多人会疑惑：为什么浏览器都能打开登录页面，VS Code 却仍然报错？

原因在于，**浏览器和 VS Code 插件并不是同一个网络环境**。

浏览器往往已经正常接管了代理设置，因此你可以顺利访问登录页；但插件发起认证请求时，未必会自动继承浏览器的代理状态，也未必能正确读取系统代理。结果就是：

- 浏览器登录成功；
- 认证回调开始执行；
- VS Code 插件尝试发起 token 请求；
- 请求没有正确经过代理；
- 于是 token exchange 阶段失败，返回 403。

因此，显式写入代理配置的意义，就是把这条网络链路补齐，让 VS Code 插件与浏览器处于一致的代理环境中。

---

### 八、仍然报错时的排查思路

如果按上述方式配置之后仍然报错，可以继续从以下几个方向排查。

#### 1. 检查代理端口是否正确

确认你的本地代理工具确实已经启动，并且监听端口确实是：

```text
127.0.0.1:7890
```

如果端口写错，或者这个端口并不是 HTTP 代理端口，那么 VS Code 即使读取到了配置，也无法正常使用。

---

#### 2. 检查 `settings.json` 是否为合法 JSON

`settings.json` 必须是合法的 JSON 格式。常见错误包括：

- 多写或少写逗号
- 花括号不匹配
- 与原有配置合并时格式出错

如果 JSON 格式本身有问题，VS Code 可能不会正确加载配置。

---

#### 3. 确认是否为地区限制问题

如果你的错误信息中除了 403 之外，还明确出现类似以下内容：

```text
Country, region, or territory not supported
```

那么这说明问题不只是代理配置，还可能涉及当前网络出口地区限制。

这种情况下，需要优先确认自己的网络环境是否符合平台访问要求。
也就是说：

- **插件没走代理**，可能导致 403；
- **当前网络地区本身不支持访问**，也可能导致 403。

二者表面现象相似，但根本原因不同。

---

#### 4. 尝试重新登录

在修改代理配置并重启 VS Code 后，建议重新走一次完整登录流程，而不是在原有报错窗口上反复重试。因为有些登录状态在失败后已经失效，重新发起流程更稳妥。
